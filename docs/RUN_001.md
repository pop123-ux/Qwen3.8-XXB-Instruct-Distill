# Run 001 — the first controlled canonical KD experiment

The real Qwen3.8-27B teacher driving the frozen 13,008,505,728-parameter canonical
student through actual knowledge distillation on one A40, measured rather than modelled.

**What this establishes:** the canonical KD mechanism is operational and its memory
footprint is now a measurement instead of an estimate.

**What it does not establish:** anything about capability. Fifty optimizer steps over
51,200 tokens cannot move a 13B model, and no capability claim is made from this run.
The loss numbers below are evidence that a gradient flowed, nothing more.

---

## The blocker this run had to clear first

The canonical student cannot be trained with full-parameter AdamW on this hardware, and
that was never in doubt:

| | GiB |
|---|---|
| bf16 weights | 24.23 |
| bf16 gradients | 24.23 |
| fp32 master + Adam moments | 145.4 |
| resident 4-bit teacher | ~16.9 |
| **required** | **~210** |
| **available (A40)** | **44.43** |

The project's config schema had advertised a way around this since it was written —
`STRATEGIES = ("full", "lora", "qlora")` — and the trainer implemented none of it:

```python
if config.training.strategy != "full":
    raise NotImplementedError(f"strategy {config.training.strategy!r} needs `peft` ...")
```

`training.optimizer` was in the same condition: validated against `OPTIMIZERS`, written
into every run summary, and ignored — the trainer built `torch.optim.AdamW`
unconditionally. A run could therefore declare `strategy: qlora, optimizer: adamw_8bit`,
have both accepted, and have neither happen. The earlier `kd_preflight` summary records
`optimizer: adamw_8bit` for a run that used `torch.optim.AdamW`.

Both are now implemented in
[`peft_support.py`](../src/qwen_distill/training/peft_support.py). **No architecture was
changed to get here**: the base model is loaded from the materialised checkpoint exactly
as written, every base weight is frozen, and the only new parameters are LoRA factors.

## What was actually run

```
teacher   Qwen/Qwen3.8-27B @ dbdc473dea0d6a9763042881cc33d6058d1742d2, NF4 4-bit
student   qwen38_19b_h5120_l48_moe, 13,008,505,728 parameters, frozen, NF4 4-bit base
adapters  LoRA r=16 alpha=32, 23,003,136 parameters (0.1765%), fp32
objective mixed_kd: 0.5 x KD + 0.5 x CE, temperature 2.0, teacher top-k 64
sequence  1024 tokens, batch 1, gradient checkpointing on, bf16 autocast
optimizer AdamW
corpus    public-domain English, tokenised by the teacher's own Qwen2Tokenizer
```

The teacher signal is **online**: a real 27B forward per step, not a cached corpus and
not a synthetic stand-in.

### The adapter reaches every layer

Adapting `q/k/v/o_proj` alone — the reflex for a dense transformer — would have touched
only 12 of 48 layers, because 36 of this student's layers are DeltaNet linear-attention
blocks with different projection names. The target set covers both:

| projection | layers | why |
|---|---|---|
| `in_proj_qkv`, `out_proj` | 36 | DeltaNet linear-attention blocks |
| `q_proj`, `k_proj`, `v_proj`, `o_proj` | 12 | full-attention blocks |

240 adapter tensors, 23,003,136 parameters, confirmed by reading the written checkpoint.

The MoE expert matrices are **excluded by scope, not by accident**. Targeting them means
384 adapters per projection, and a top-2 router means most would receive near-zero
gradient. The expert weights are present, frozen, and used in every forward pass.

## Measured memory

Sequence 1024, batch 1, both models resident, on a 44.43 GiB A40.

| | GiB |
|---|---|
| peak allocated | **37.79** |
| peak reserved | **38.30** |
| total available | 44.43 |
| headroom | ~6.1 |

An engineering note worth recording: bitsandbytes quantises `nn.Linear` modules, and
this architecture stores its MoE experts as stacked `nn.Parameter` tensors consumed by a
grouped-matmul kernel. Those ~4.5B expert parameters therefore stay bf16 through a
4-bit load, and the student lands near 17 GiB rather than the ~10 GiB a naive
"13B at 4 bits" calculation predicts. The run fits anyway; a longer sequence might not.

**This is a training measurement on a 48 GB card. It is not a deployment number** and
says nothing about the 16 GB student target, which concerns the student alone at
inference precision.

## What happened

Two runs, same configuration, different lengths.

**Smoke — 1 step.** Exit 0. `loss 9.7841 = 0.5 x kd 9.1831 + 0.5 x ce 10.3852`, every
value finite, optimizer step applied, checkpoint written and validated at `load` level.
This is the complete record: `runs/run001_kd_smoke/summary.json`.

**Pilot — 50 steps.** All 50 optimizer steps completed, 51,200 tokens in 598.8 s.

| step | loss | KD | CE | top-1 agreement |
|---|---|---|---|---|
| 2 | 9.9119 | 9.5148 | 10.3090 | 0.001 |
| 50 | 4.9593 | 3.6622 | 6.2563 | 0.139 |

Validation loss fell monotonically at every evaluation: 7.6873 → 6.8782 → 6.4255 →
6.3664. Checkpoints at step 25 and step 50, both validated at `structure`, `manifest`
and `load` level.

Teacher diagnostics stayed stable across the run — entropy ~1.31, tail mass beyond the
top-64 shortlist ~0.65. That tail mass is the number [REAL_TEACHER_RUN.md](REAL_TEACHER_RUN.md)
says gates the offline-logit decision (B6): two thirds of the teacher's probability mass
sits outside a 64-entry shortlist, so an offline corpus at k=64 would discard most of the
distribution.

**The pilot has no `summary.json`, and the reason is a defect of mine.** The summary
writer raised `NameError: param_report` after the final checkpoint was written: the
change that added `parameter_counts` to the summary assigned the name in `train()` and
read it in `_write_summary()`, a different scope. The pilot had already imported the
broken module when the fix landed. Training completed; only the derived summary was
lost. The fix is in and covered by the checkpoint test suite, and the per-step evidence
survives in `metrics.jsonl`, which is written and fsynced as the run proceeds. The
memory profile quoted above therefore comes from the smoke run, which ran the identical
configuration to completion.

Neither run says anything about capability, and neither is offered as evidence of any.

## Reproducing it

```bash
python scripts/kd_run.py \
    --teacher /workspace/models/qwen3.8-27b-dbdc473 \
    --revision dbdc473dea0d6a9763042881cc33d6058d1742d2 \
    --quantization 4bit \
    --student canonical --pretrained /workspace/runs/pilot001/transferred \
    --text-path /workspace/corpora/gutenberg/train.txt \
    --sequence-length 1024 --max-tokens 200000 \
    --steps 50 --batch-size 1 \
    --objective mixed_kd --kd-weight 0.5 --kd-temperature 2.0 --kd-top-k 64 \
    --strategy qlora --optimizer adamw --lora-rank 16 --lora-alpha 32 \
    --precision bf16 --seed 0 \
    --output /workspace/runs/run001_kd_pilot
```

`--strategy full` remains available and will still fail on this hardware, as it should.

## Checkpoints

A parameter-efficient run writes `adapter_model.safetensors` — 92 MB — instead of
`model.safetensors`. Writing the whole model would serialise a frozen 13B base on every
save, 25 GB per checkpoint identical to the materialised student already on disk, and
for a 4-bit base it would write packed `uint8` blobs that do not reconstruct the weights
once separated from their `quant_state`.

The checkpoint validator was taught this: the weights requirement is satisfied by
whichever file the checkpoint's own metadata says it wrote, and the size-plausibility
bands scale by the trainable count rather than the frozen base. Deletion is still
detected. Validated at `structure`, `manifest` and `load` level, and the adapter reloads
to exact equality.
