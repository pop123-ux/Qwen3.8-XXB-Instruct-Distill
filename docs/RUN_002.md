# Run 002 — the pure logit-KD control, stopped at its memory gate

Run 002 was to be the project's first **controlled distillation comparison**: a
conventional pure-logit-KD arm, measured, that later layer-KD and
computational-behaviour/state-KD arms could be matched against.

**It did not run.** The 128-step control was stopped by its own pre-declared safety gate.
One 2048-token calibration step measured **43.014 GiB peak allocated** against a **42.0
GiB** gate declared before the run, so the control was not launched. This document records
the measurement that stopped it, because that measurement is the result.

**What this establishes:** what a 2048-token pure-logit-KD step on the canonical student
actually costs on an A40, and — with Run 001's 1024-token measurement — how that cost
scales with sequence length. Both are measurements, not estimates.

**What it does not establish:** anything about capability, and nothing about logit KD as
an objective. One step is a memory probe.

**What it is explicitly not:** a comparison against Run 001. Run 001 is the
mechanism-validation pilot and stays documented as exactly that. The two runs differ in
objective, sequence length and step count simultaneously; no difference between them
attributes to any single cause.

---

## The intended experiment

```
teacher   Qwen/Qwen3.8-27B @ dbdc473dea0d6a9763042881cc33d6058d1742d2, NF4 4-bit
          online logits, top-k 64, temperature 2.0
student   qwen38_19b_h5120_l48_moe, 13,008,505,728 parameters, frozen, NF4 4-bit base
adapters  LoRA r=16 alpha=32, 23,003,136 parameters (0.1765%)
objective logit_kd — alpha 1.0, pure KD, CE contributes nothing
sequence  2048 tokens, batch 1, accumulation 1, 128 steps, seed 0
optimizer AdamW, bf16 autocast, gradient checkpointing on
```

Nothing in the architecture, the teacher, the student, the LoRA geometry or the tokenizer
was changed to set this up. The only code added was three CLI flags on `kd_run.py`
(`--log-every`, `--eval-every`, `--save-every`) so that metrics could be persisted **per
step** as the run specification required; the derived default would have logged every 6th
step at 128 steps.

### `logit_kd` is exactly pure KD

`distillation_loss` computes `alpha * KD + (1 - alpha) * CE` and `logit_kd` sets
`alpha = 1.0`, so cross-entropy contributes nothing to the gradient. It is still computed
and logged every step as a diagnostic. The calibration step confirms this arithmetically:

```
loss 6.5997  =  kd 6.5997        (ce 10.3545 logged, unweighted)
```

## The gate, and why it existed

Run 001 measured 37.788 GiB peak allocated at sequence 1024. Doubling the sequence was
never going to be free, and the failure mode of finding out the expensive way is an OOM
30 minutes into a run that has already paid for a teacher load. So the run specification
fixed a threshold in advance — peak allocated over 42 GiB means stop — and one step was
run to measure it.

### What was verified before the calibration was allowed to start

| check | result |
|---|---|
| git clean | 0 tracked modifications at `779da74` |
| teacher revision | `dbdc473dea0d6a9763042881cc33d6058d1742d2`, 55.59 GB, from the download manifest |
| canonical student | `model.safetensors` sums to **13,008,505,728** parameters exactly |
| student geometry | 48 layers, 36 `linear_attention` + 12 `full_attention`, `[D,D,D,A] x 12`, vocab 248,320, 8 experts top-2, shared expert 768, untied |
| PEFT configuration | QLoRA r=16 alpha=32 over the same 6 projections as Run 001 — geometry unchanged |
| corpus | 341 sequences of 2048 (324 train / 17 validation) — enough that 128 steps do not wrap the epoch |

## The measurement

One 2048-token step, exit 0, `/workspace/runs/run002_calibration`:

| | GiB |
|---|---|
| total VRAM (A40) | 44.432 |
| **peak allocated** | **43.014** |
| **peak reserved** | **43.541** |
| headroom at peak | 1.42 |

```
step 1  loss 6.5997  kd 6.600  ce 10.354  agree 0.0005  tail 0.708   139 tok/s   14.7 s
        validation 9.8153
```

Teacher entropy 1.3466. Tail mass beyond the top-64 shortlist **0.708** — higher than the
0.654 measured at sequence 1024, and further evidence for the B6 finding that an offline
logit corpus at k=64 would discard most of the teacher's probability mass.

### Where the memory goes

Stage-by-stage peak allocated, against Run 001's identical stages at sequence 1024:

| stage | seq 1024 | seq 2048 | delta |
|---|---|---|---|
| baseline (4-bit teacher resident) | 16.441 | 16.441 | 0.000 |
| after model creation (+ student, + optimizer) | 32.597 | 32.597 | 0.000 |
| after forward | 34.944 | 37.321 | +2.377 |
| after loss | 36.413 | 40.218 | +3.805 |
| after backward | 37.788 | **43.014** | +5.225 |

The split is clean:

* **32.597 GiB is sequence-independent** — the 4-bit teacher, the 4-bit student and the
  optimizer state. It does not move with sequence length at all.
* **The remainder scales linearly**: 5.192 GiB at 1024, 10.417 GiB at 2048 — a ratio of
  **2.006** for a 2x sequence increase. About 5.09 MiB per token, dominated by the
  248,320-wide logits: 1.89 GiB per fp32 copy at this sequence length, and the KD path
  materialises them in fp32 for the teacher (twice, in `capture_signal`) and for the
  student (in `distillation_loss`), on top of the bf16 originals.

Extrapolating that line:

| | max sequence |
|---|---|
| under the 42 GiB gate | **1848 tokens** |
| under the 44.43 GiB card, zero margin | 2326 tokens |

So 2048 sits *between* the gate and the hard limit. It runs — the calibration proves that
— but with 1.42 GiB of headroom and 0.89 GiB on the reserved figure. That is what the gate
was for.

## What was not done

**The sequence length was not reduced to make it fit.** 1848 tokens would have passed the
gate, and it would have been a different experiment than the one specified — quietly
substituted at the moment the specified one became inconvenient. The run specification
said to stop and report the measured value, so that is what happened.

**No 128-step run was started.** No capability claim is made, and none is available.

## Reproducing the calibration

```bash
PYTHONPATH=src PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True python -u scripts/kd_run.py \
    --teacher /workspace/models/qwen3.8-27b-dbdc473 \
    --revision dbdc473dea0d6a9763042881cc33d6058d1742d2 \
    --quantization 4bit \
    --student canonical --pretrained /workspace/runs/pilot001/transferred \
    --text-path /workspace/corpora/gutenberg/train.txt \
    --sequence-length 2048 --max-tokens 700000 \
    --steps 1 --batch-size 1 --gradient-accumulation-steps 1 \
    --objective logit_kd --kd-weight 1.0 --kd-temperature 2.0 --kd-top-k 64 \
    --strategy qlora --optimizer adamw --lora-rank 16 --lora-alpha 32 \
    --precision bf16 --seed 0 --log-every 1 \
    --output /workspace/runs/run002_calibration
```

`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` is not optional for comparability: it
is what Run 001 ran under, and it materially changes the reserved figure.

## What would let the control run

These are options, not decisions — none of them has been taken, and each changes something
the run specification froze.

| | effect on peak | what it costs |
|---|---|---|
| sequence 1848 or below | passes the gate | a different experiment than the one specified |
| offline teacher logits | removes 16.44 GiB of resident teacher | gated on B6, and tail mass 0.708 says k=64 is not enough |
| `adamw_8bit` | 0.13 GiB | pointless here: the optimizer state covers 23M adapter parameters, not 13B, so fp32 moments are only 0.17 GiB to begin with |
| a larger card | passes at 2048 | outside the current hardware |

The cheapest honest path is the second, and it is already the open question B6 was waiting
on. The tail-mass number this run adds — 0.708 at sequence 2048 — makes that decision more
pressing, not less.
