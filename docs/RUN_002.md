# Run 002 — the pure logit-KD control

The conventional pure-logit-KD arm the project's later comparisons are measured against.
128 optimizer steps of the real Qwen3.8-27B teacher driving the frozen
13,008,505,728-parameter canonical student at sequence 1536, on one A40.

**What this establishes:** a conventional logit-KD reference point on the canonical
student — its loss trajectory, its teacher-agreement trajectory, its throughput and its
memory footprint at a context 1.5x Run 001's, all measured.

**What it does not establish:** anything about capability. 128 optimizer steps over
196,608 tokens cannot move a 13B model, and no capability claim is made from this run.

**What it is explicitly not:** a comparison against Run 001. Run 001 is the
mechanism-validation pilot (mixed_kd alpha 0.5, sequence 1024, 50 steps) and stays
documented as exactly that. The two runs differ in objective, sequence length and step
count simultaneously, so no difference between them attributes to any single cause.

## What ran

```
teacher   Qwen/Qwen3.8-27B @ dbdc473dea0d6a9763042881cc33d6058d1742d2, NF4 4-bit
          online logits, top-k 64, temperature 2.0, exact tail via full-vocab logsumexp
student   qwen38_19b_h5120_l48_moe, 13,008,505,728 parameters, frozen, NF4 4-bit base
adapters  LoRA r=16 alpha=32, 23,003,136 parameters (0.1765%)
objective logit_kd — alpha 1.0, pure KD, CE contributes nothing to the gradient
sequence  1536 tokens, batch 1, accumulation 1, 128 steps, seed 0
optimizer AdamW, bf16 autocast, gradient checkpointing on
corpus    public-domain English, tokenised by the teacher's own Qwen2Tokenizer
          455 sequences of 1536 (433 train / 22 validation)
```

Everything except the sequence length and the objective is identical to Run 001. The
teacher, its revision, the student geometry, the LoRA target set, the tokenizer, the
corpus, the seed, the temperature and the top-k were not touched.

### `logit_kd` is exactly pure KD

`distillation_loss` computes `alpha * KD + (1 - alpha) * CE` and `logit_kd` sets
`alpha = 1.0`, so cross-entropy contributes nothing to the gradient. It is still computed
and logged every step as a diagnostic, and every logged step confirms the arithmetic:

```
step 128   loss 1.4101  =  kd 1.4101        (ce 4.8790 logged, unweighted)
```

## Why 1536, and how it was chosen

Run 002 was originally specified at sequence 2048. **It did not run at 2048.** A one-step
calibration measured 43.014 GiB peak allocated against a 42.0 GiB gate declared before the
run, and the 128-step run was correctly not started. That measurement stands and is
archived at [`experiments/run002_calibration/`](../experiments/run002_calibration/).

The sequence length was then **re-declared at 1536 before anything was launched**, not
reduced part-way through a run and not reduced to rescue a failing one. The choice came
from the two measured points:

| | GiB |
|---|---|
| sequence-independent base (4-bit teacher + 4-bit student + optimizer) | 32.597 |
| marginal cost | 5.226 MiB/token |

which puts the gate at 1848 tokens and the bare card at 2326. 1536 was taken rather than
1792 because 1792 clears the gate by 0.29 GiB, a margin inside allocator noise. The line
predicted **40.401 GiB** at 1536; the calibration measured **40.401 GiB**.

### The gate was re-measured, not extrapolated

One 1536-token step, exit 0, `/workspace/runs/run002_calibration_1536`:

| | GiB |
|---|---|
| **peak allocated** | **40.401** |
| peak reserved | 40.945 |
| gate | 42.000 |
| margin | **+1.599** |

The 128-step control was launched immediately on that result, with no pause.

## What happened

All 128 optimizer steps completed. Exit code 0, no OOM, 196,608 tokens in 1283.2 s.

| step | loss | KD | CE | top-1 agreement | tail mass |
|---|---|---|---|---|---|
| 1 | 7.1902 | 7.1902 | 10.9596 | 0.0065 | 0.7046 |
| 16 | 3.2985 | 3.2985 | 9.3910 | 0.0612 | 0.7058 |
| 32 | 2.4006 | 2.4006 | 7.4381 | 0.1492 | 0.7262 |
| 64 | 1.5994 | 1.5994 | 5.2399 | 0.3016 | 0.7064 |
| 96 | 2.6643 | 2.6643 | 4.8296 | 0.2899 | 0.6451 |
| 128 | 1.4101 | 1.4101 | 4.8790 | 0.3375 | 0.7075 |

Per-step loss at batch 1 is noisy — step 48 reads 4.41 between a 2.40 and a 1.60 — so the
trajectory is better read in aggregate, where it is unambiguous:

| | first 16 steps | last 16 steps |
|---|---|---|
| mean loss | 6.3268 | **2.1365** |
| mean top-1 agreement | 0.0406 | **0.3047** |

Validation loss fell at every evaluation: **7.2044 → 5.3499 → 5.1348 → 5.0334**.

The unweighted CE diagnostic fell monotonically in aggregate too, 10.96 → 4.88, which is
the check that matters for an alpha=1.0 run: the student is not merely matching the
teacher's shortlist ordering while drifting as a language model.

Teacher diagnostics stayed stable, as they must — the teacher is frozen and the corpus is
fixed. Entropy ~1.33 nats mean, tail mass beyond the top-64 shortlist **0.667 mean**.

### Tail mass, and what it keeps saying

Tail mass at 1536 averages 0.667, between Run 001's 0.65 at sequence 1024 and the 0.708
measured at 2048. Two thirds of the teacher's probability mass sits outside a 64-entry
shortlist at every sequence length tried. This is the number that gates the offline-logit
decision (B6): an offline corpus at k=64 would discard most of the distribution. Run 002
does not resolve that question, it adds a third point saying the same thing.

## Measured memory

Sequence 1536, batch 1, both models resident, on a 44.432 GiB A40.

| | GiB |
|---|---|
| **peak allocated** | **40.580** |
| **peak reserved** | **43.127** |
| total available | 44.432 |
| gate | 42.000 |

Stage by stage, against the two calibrations:

| stage (peak allocated) | seq 1536 | seq 2048 |
|---|---|---|
| baseline (4-bit teacher resident) | 16.441 | 16.441 |
| after model creation (+ student, + optimizer) | 32.597 | 32.597 |
| after forward | 36.132 | 37.321 |
| after loss | 38.315 | 40.218 |
| after backward | **40.401** | **43.014** |

The control's peak allocated (40.580) sits 0.179 GiB above its own calibration (40.401);
the extra appears after step 1, from the validation passes and checkpoint writes that a
one-step calibration never reaches.

**Peak reserved is the figure to watch, not peak allocated.** At 43.127 GiB it is 2.18 GiB
above the calibration's 40.945, because the caching allocator grows across 128 steps and
four validation passes in a way one step does not reveal. It leaves 1.30 GiB of headroom
on the card. The gate is declared on allocated and was met with 1.42 GiB to spare, but a
future run at a longer context should expect reserved, not allocated, to be what binds.

### An engineering finding, measured and not adopted

The peak is set by the backward pass through the KD loss, which materialises several
full-vocabulary fp32 tensors at 248,320 wide — 1.421 GiB each at sequence 1536, 1.894 GiB
at 2048.

At `alpha = 1.0` the CE diagnostic is multiplied by exactly zero, yet building it inside
the autograd graph pins one such copy until backward has run. Computing it detached was
verified bit-identical in both value and gradient, across dense and sparse signals, both
tail treatments and alpha in {0.0, 0.5, 1.0}.

The figures below were probed at the 2048 shapes, because 2048 is the length the question
was being asked about.

**It was measured and not adopted, because it does not move the peak.** Retained memory
falls from 3.789 to 1.896 GiB, but peak-through-backward stays at 8.521 GiB above the
post-forward baseline in both cases: the peak is the KD path's own backward transients,
not CE retention. The synthetic probe reproduces the real run to within 0.04 GiB
(43.014 − 34.535 = 8.479 measured), so this is a reliable negative result, and it rules
out the cheapest candidate fix. Getting 2048 under the gate needs the KD backward itself
chunked over positions — a real change to the objective's implementation, and not one to
make to a control arm mid-ladder.

## Reproducing it

```bash
PYTHONPATH=src PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True python -u scripts/kd_run.py \
    --teacher /workspace/models/qwen3.8-27b-dbdc473 \
    --revision dbdc473dea0d6a9763042881cc33d6058d1742d2 \
    --quantization 4bit \
    --student canonical --pretrained /workspace/runs/pilot001/transferred \
    --text-path /workspace/corpora/gutenberg/train.txt \
    --sequence-length 1536 --max-tokens 700000 \
    --steps 128 --batch-size 1 --gradient-accumulation-steps 1 \
    --objective logit_kd --kd-weight 1.0 --kd-temperature 2.0 --kd-top-k 64 \
    --strategy qlora --optimizer adamw --lora-rank 16 --lora-alpha 32 \
    --precision bf16 --seed 0 \
    --log-every 1 --eval-every 32 --save-every 64 \
    --output /workspace/runs/run002_logit_kd
```

`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` is not optional for comparability: it
is what Run 001 and both calibrations ran under, and it materially changes the reserved
figure.

## What this unblocks, and what it does not

Run 002 is Baseline B on the ladder. Baseline C (layer / intermediate KD) and the
computational-behaviour / state-KD arm are now measurable against something.

For those comparisons to mean anything they must hold **sequence length 1536, 128 steps,
batch 1, seed 0, the same corpus and the same teacher** fixed, and vary only the objective.
Run 002 exists to be that fixed point. Anything that changes two axes at once is not a
comparison against it.

**Run 003 has not been started.**
