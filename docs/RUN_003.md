# Run 003 — Layer / Intermediate KD control

**Status: STOPPED at the memory gate. The 128-step run was not launched.**

Run 003 is the matched partner of Run 002. Everything is held equal and the single
intended difference is the distillation objective:

| | Run 002 | Run 003 |
| --- | --- | --- |
| objective | pure logit KD | pure layer / intermediate KD |
| supervision | KL(teacher ‖ student) over the output distribution | pointwise hidden-state matching at 48 mapped layer pairs |
| everything else | — | identical |

The objective is defined in full in [LAYER_KD.md](LAYER_KD.md) and copied into the run
record under `distillation.layer_kd_definition`.

## Where the memory went

Both objectives run the same teacher, the same quantised student, the same optimizer and
the same batch. The stage profile locates the whole difference in the loss:

| stage | Run 002 | Run 003 |
| --- | ---: | ---: |
| baseline (resident 4-bit teacher) | 16.4414 | 16.4414 |
| after model creation | 32.5967 | 32.5967 |
| after forward | 36.1323 | 37.3225 |
| **after loss** | **38.3154** | **42.5354** |
| after backward | 40.4010 | 42.5354 |

Two costs, both intrinsic to the objective rather than to this implementation:

1. **The teacher must return its hidden states.** 65 tensors of (1, 1536, 5120); about a
   gigabyte, and the reason `after_forward` is 1.19 GiB higher. It is dropped as soon as
   the loss is built, so it does not persist into the backward pass.
2. **Both sides' hidden states are held through the backward pass.** The loss compares 48
   pairs, and `mse_loss` saves both of its normalised float32 inputs for backward: 48 × 2 ×
   (1536 × 5120 × 4 bytes) ≈ 3.0 GiB that cannot be freed until the gradient is computed.
   This is why `after_loss` is 4.22 GiB higher and why the peak sits at the loss rather
   than at the backward pass, which is where logit KD peaks.

Gradient checkpointing does not help here: the retained tensors are loss inputs, not layer
activations.

## What the calibration nevertheless established

The step ran to completion, so the objective and its plumbing are verified even though the
128-step run did not launch:

- The layer map built at runtime is the documented one — **48 pairs, 16 teacher layers
  unsupervised** (8–11, 24–27, 36–39, 52–55).
- The optimised loss is the layer term: `loss 1.4501 = magnitude 0.9668 + direction
  0.4834`, and not the KD divergence reported beside it (7.190).
- `layer_norm_ratio` at step 1 is **0.5238** — the student's mapped hidden states carry
  roughly half the teacher's activation norm at initialisation. A magnitude-dominated
  objective at the start, which is what the separate magnitude/direction reporting exists
  to show.
- **The arms are genuinely matched.** Run 003's step-1 KD diagnostic is `7.190154` and Run
  002's step-1 KD loss is `7.190154`, to six decimal places. Same seed, same batch, same
  teacher, same student initialisation — the two runs saw an identical first step and
  differ only in what was optimised from it.

## Options, none of them taken

Every way forward changes something the comparison depends on, so none was chosen here.
The decision belongs to the project owner.

1. **Raise the gate to ~43 GiB.** The measurement fits the card (44.10 GiB reserved against
   44.43 usable) with 0.33 GiB of headroom. The gate is a safety margin, not a hardware
   limit, and it was set for a different objective. But 0.33 GiB is thin: allocator
   fragmentation over 128 steps is exactly the risk the margin exists for, and an OOM at
   step 90 would waste more budget than a rerun.
2. **Reduce the sequence length.** Explicitly forbidden — it would break the match with Run
   002 and is the reason the instruction says not to do it silently.
3. **Reduce the number of supervised pairs** (for example, one pair per hybrid group rather
   than all 48). This would cut the retained loss inputs roughly four-fold and comfortably
   clear the gate, but it changes the objective, so Run 003 would no longer be *the*
   conventional layer-matching control.
4. **Compute the layer term in chunks over positions**, accumulating gradient per chunk.
   This is numerically the same objective and would cut peak memory substantially, but it
   is new training-loop machinery that would have to be written and validated first, and
   Run 003 would then be measuring code written for it rather than the existing A1 control.

Option 1 is the only one that leaves the science untouched. Option 4 is the only one that
buys real headroom without touching the science, at the cost of new code.
